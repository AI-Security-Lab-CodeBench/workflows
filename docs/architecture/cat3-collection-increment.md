# CAT-3 collection increment

Historical design record. The four-stage template and path-bearing declaration
examples below are superseded for new runs. Use the [active collection graph](cat3-collection-flow.md)
and [stage reference](../pipeline-stages.md) for current behavior.

**Status:** The independent [review](cat3-collection-review.md) passed and the human owner approved the [revised Mermaid flow](cat3-collection-flow.md) for implementation on November 18, 2026. Source eligibility, QA and release authorization still require their own evidence.

**Production target:** The existing `cloud_infrastructure_commands_grounded_v1` partition of `dataset_builds`, with one `datasets/dataset_release`. Keep the current corpus and documentation scopes, add at least two independent eligible corpus origins, and add a Keenable administrative-use-case branch. Guarded labeling consumes candidate provenance and acquires other evidence on demand; it retains verified snippets and receipts with attempts. Release requires the current outputs of all configured branches and the existing labeling and review gates.

## Baseline and decision

`dataset_bundle.py` resolves prepared branch manifests into lists of `SourceSeed` files and resolves `finalization.documentation` into a config containing snippet text. The registry snapshots that resolved spec; `definitions.py` puts it into the global config asset. The local manifests have 274 files from **one** `cheat/cheatsheets` corpus, 13,067 documentation files (7,262 tldr pages and 5,805 AWS CLI files), and 1,052 separately declared semantic snippets. These are input counts, not eligible, materialized or published counts. Some snippets refer to the same tldr and AWS origins; “separately declared” does not mean independently authored. The shipped `business-configs/datasets/cat3.json` has `batch: null`; it is not evidence of the live spec or a safe replacement for it.

`dataset_branches.py`, `dataset_plan.py`, `dataset_run.py`, `definitions.py` and `dataset_finalization.py` currently enumerate two branches or dispatch on the literal documentation namespace. The source asset factory in `dataset_assets_sources.py` runs catalog, snapshot, adapter and extraction stages. `dataset_documentation.py` builds the shared `DocumentationTable` from provided snippets and reports coverage using `dataset_documentation_models.py`. `labeling_attempts` then accounts for all filter-eligible rows, and `release_runner.py` drives the single release through the persisted review workflow. The legacy discovery graph (`discovery_assets.py`, `legacy_definitions.py`) is not the active dataset graph.

| Viable design | Coupling and tests | Migration and failure modes |
| --- | --- | --- |
| **Extend the active asset graph** with one branch descriptor table, source declarations and typed persisted evidence. Keep branch-local acquisition and shared finalization. | Reuses the typed table, selective planner, I/O and review contracts. Test acquisition with fixtures and prove invalidation and release admission at one existing seam. | Keeps partition and asset identities; requires explicit compatibility with prepared manifests and checks on every path to current data. A failed configured branch blocks a new unified release. |
| **Run a separate Dagster acquisition job family** with its own partitioned catalog and signed-off batch handoff. Main dataset imports one immutable bundle per branch. | Acquisition workers and retries are isolated. Both programs need independent tests plus handoff and revocation contract tests. | Easier to isolate provider outages, but importing bundles adds a second currentness authority, new scheduling and recovery coordination, and a second set of partition identities. A healthy import can hide a stale acquisition unless both sides validate it. |

Choose the first design. One graph already supplies lineage, artifact currentness and release authorization. A typed descriptor for three fixed branches is enough; no plugin manager, external handoff service, generic crawler or new review ledger. The trade-off is that Keenable health and source drift become visible release blockers. Bound those dependencies and support exact replay instead of weakening publication.

## Ownership and configuration

The controlling decision is the user's revision instruction: “User explicitly authorized branch-owned acquisition in the declared-source graph.” The current written policy in `AGENTS.md`, `docs/independent-branches.md` and `skills/codebench-source-preparation/SKILL.md` still requires local discovery, complete enumeration and source assessment for prepared manifests, with no pipeline source search. Historical registrations keep that flow, including prepared-source provenance, license/reuse and integrity checks; this design neither changes those checks nor edits current policy.

After independent rereview and human diagram approval, the first implementation change is a narrow CAT-3 exception in those three files and matching source-list documentation. The source steward approves origin, exact scope, pins, reuse/retention rights, attribution, parser identity, seed allowlists and new generations. Any exception within this permitted scope requires an explicit versioned steward decision; unresolved rights or unsafe content cannot be overridden by runtime. Dagster deterministically enumerates declared scopes, verifies terms/notice evidence and approved use, validates integrity, withholds disallowed inputs and acquires, transforms and persists permitted evidence. Only the declared Keenable branch searches for collection sources; corpus and documentation enumerate approved declarations without search. Label-time evidence lookup is bounded and does not add collection sources. There is no selector or adapter model, per-file local inventory prerequisite for the declared-source graph, or active `human_source_decisions` stage. Source stewardship does not approve commands for release.

Add a strict source-declared bundle alongside readable historical specifications. Keep `existing_datasets`, `documentation_crawl` and new `keenable_use_cases` explicit in the bundle; use category-owned companion config files for their source lists, seed text, family coverage questions and trust rules. Keep `category.json` and its current labeling-policy files authoritative for taxonomy and classification. Store only normalized declarations and digests in the registered spec and config assets:

- Each branch config must reference its own source list. Every origin declares stable ID and provenance, exact repository roots at an immutable commit, include/exclude and regular-file predicates **or** exact HTTPS URL with SHA-256, parser or mapping and options, pinned rights/origin evidence and notices, permitted use and attribution, and explicit refresh and failure rules. For Keenable the reference carries seed and destination scope, and the frozen selection supplies exact URLs. Resolve and hash declarations without enumeration, fetch or Python execution at registration. Refresh requires a new steward-approved revision/pin or discovery generation. Failure to enumerate a declared root, verify required evidence, or fetch/verify an admitted file blocks currentness; a deterministically withheld record has a reason and does not count as an admitted file. Use the versioned rights policy to decide candidate, semantic-only or withheld scope.
- An ETL entry uses the existing `SourceTransformConfig` fields (`module_path`, `sha256`, `entrypoint`, `kind`, `trusted`, `options_json`, `batch_size`). A separately reviewed deployment allowlist binds the resolved contained path (no escaping symlink), module digest, entrypoint, and locked dependency/runtime revision. Caller-supplied `trusted: true` and matching bytes alone grant no authority. Reuse `source_transform_contract.py` and `source_transforms.py`; validate before import, then centrally validate `CanonicalSourceRow`, source position and transformations. Test an unapproved module with the correct supplied digest. No downloaded code, shell execution, implicit imports from captures, fabricated arguments, clock or network calls in ETL.
- Keenable collection declarations carry stable seed IDs, allowed HTTPS hosts/path prefixes, candidate use and retention rights, priority buckets by category family, budget and explicit discovery generation. Labels and command bodies never come from search results. Cite branch evidence only through the candidate's own provenance and approved citation rights. Put label-time provider limits, applicability and trust settings under `finalization.annotation.batch.grounding`. The source declaration rejects `finalization.documentation` and embedded or referenced snippet lists. Demonstrations remain illustrative and cannot ground candidate labels.

### Keenable governance

Use `GroundingBroker`'s Keenable trust, bounds and transport patterns in the active graph; share the provider client and URL policy instead of invoking an annotation worker or the legacy discovery graph. Collection runs deterministic category queries with no inference or tool-calling agent. Initial allowlist: official Kubernetes, Docker, HashiCorp Terraform, AWS and PostgreSQL docs (`kubernetes.io/docs/`, `docs.docker.com/`, `developer.hashicorp.com/terraform/`, `docs.aws.amazon.com/`, `www.postgresql.org/docs/`). Configure one seed for each coverage area: infrastructure plan/validation; workload inventory/status; container status/storage usage; storage or SQL inspection and scope; deployment rollout status/health. Each seed combines the family with neutral questions such as “What does the documented status request observe, what scope does it use, and which version or flags change that scope?” and “What does the documented preview mode report, and when does it make changes?” Do not feed filtered candidates back into collection or send raw candidates, resource names or environment context to search. Avoid exploit, evasion, intrusion or real-target workflows and collection of exploit instructions.

**Discovery and authoritative origin capture.** Keenable search supplies ranked lead URLs only. The existing broker fetch returns bounded provider `content` and validates the provider hop; neither proves bytes or redirects at the origin. Use a separate bounded direct HTTPS origin-capture client in `source_retrieval.py`, invoked by `datasets/keenable/source_documents`. Canonicalize by lowercasing the DNS name and discarding the fragment; require port 443 and a normalized path inside an exact allowlisted host/prefix. Reject userinfo, ambiguous encodings, traversal and queries unless the declared rule permits that exact parameter set. Revalidate at fetch, connect only to a verified public destination for that host with normal TLS verification, and reject every redirect. Accept only complete direct success bodies of declared types, requested with identity encoding; reject partial, transformed, truncated, oversized or transfer-incomplete payloads. Hash the verified body with SHA-256 and retain byte offsets; derived text must resolve back to an exact span. Use runtime credentials for the provider only, never for origin requests. Precheck permission to fetch before sending; verify current terms, content and retention scope before persistence or model use. If policy withholds a page, keep only safe metadata and reason. Do not retain or forward prohibited text, execute retrieved content or render it as active markup.

**Generation ledger and failure transitions.** Serialize each generation and reserve the complete call and byte allowance before dispatch. Revision 2 bounds collection using the registered source declaration, including deduplicated license captures. The current generation permits 2 searches, 23 origin requests and 13,107,200 bytes; it does not inherit the historical 20-call limit. Reject a declaration whose configured seeds and required license captures cannot fit, and never dispatch a request beyond the registered limits. Persist attempted, successful, failed and indeterminate slots.

On restart reuse committed search results and verified captures, and send only reservations for slots that were never dispatched (a reservation left in flight is ambiguous; charge it as used, mark the slot failed, and do not resend). A definitive transport, integrity or origin failure on a selected capture also marks the generation failed; retain successful authorized captures and diagnostics but do not publish a partial lock. An ambiguous search or capture, failed selected capture, pin change or changed authorization requiring a recrawl needs a new reviewed generation. A healthy zero-result generation and a policy-withheld page are valid terminal observations distinct from transport failure. Publish the immutable lock once by compare-and-set after all slots terminate successfully or with policy exclusions; bind its selection, capture digests, rights decisions and receipts. Replaying it verifies the lock and objects locally with zero network. Test healthy zero, withheld, selected failure, over-budget refusal, interrupted reservation and concurrent resume, single lock publication, and zero-network replay.

### Guarded labeling and evidence admission

Set `source_weights` by repository origin ID and `keenable_source_weight` for
the shared Keenable branch in
`business-configs/categories/cat3/collection/repositories.json`. The weights
must be finite numbers between 0 and 1. Every documentation weight must exceed
every dataset weight, and every dataset weight must exceed the Keenable
weight. Older declarations default to 0.90 for documentation, 0.60 for
datasets, and 0.30 for Keenable. The merge records the effective value as
`source_weight` without changing the canonical command CSV.

Schedule the strongest source weights first and cluster pending commands within
each weight tier by semantic embedding. A subrisk stops taking new work at
250 distinct normalized commands with accepted, all-high labels. An ambiguous
candidate remains eligible while any compatible subrisk is open and earns credit
only for its verified label's subrisk. The `labeling-quota.json` receipt reports
shortages for the current eligible inputs and records which subrisks were full.
Deferred candidates are counted separately from labeling failures. A logical
batch shares one retrieval budget across LangGraph steps, all rows, and any
context splits: at most ten outbound provider and origin requests in total.
Generating command vectors is for grouping only; it does not retrieve passages.

Run one validator at registration and again before the `labeling_attempts` asset dispatches or serves a cache hit. Require enhanced `openai_compatible` batch config, a pinned backend revision and model identity, context and batch limits, bounded provider calls/turns, trusted evidence policy, and the endpoint's shared capacity directory and guard configuration. CLI, native jobs and manually selected assets validate the same registered spec and use the same dispatch; the declared-source graph never enters the `batch is None` baseline path in `labeling_tables.py`, including when metrics are unavailable or batch work fails. Historical prepared configurations retain that path. Every remote inference turn needs fresh verified endpoint telemetry, at most 50% of measured slots and tokens, and at most one owned in-flight request. Stale/missing telemetry or side load starts no new inference. Quarantine ambiguous requests until request-specific termination is verified.

Use the row's command and source span to verify its provenance. The declared Keenable branch owns discovery, rights checks and origin acquisition. Labeling consumes the resulting frozen captures and the independently verified repository documentation; it cannot issue another Keenable request. A search snippet alone is never evidence.

Apply the same evidence checks before inference, on cache reuse and at release. Check the command path, significant flags, scope and relevant version, and bind each citation to its exact source bytes. Try the candidate’s own admissible source first. A shared index can locate a matching documented operation and explicit operand slot; it cannot authorize an unrelated operation. Record unsupported evidence as a failure and quota deferrals separately.

Bind reuse to the logical row, its provenance, exact verified evidence/receipts and relevant policy/model/implementation identity. Reuse a prior labeling success only if those inputs still match and its bytes, applicability and rights revalidate without another lookup. A missing, changed or revoked source cannot restore success even if its quote still matches; re-ground within budget or record failure. Unrelated neighbor changes reuse valid outcomes and original receipts. Test both provider routes with no preloaded passages, valid receipt reuse with zero calls, missing batch settings and denied inference through CLI and native selection, provider-only rejection, rights revocation and unaffected-row reuse. Account for gaps, turns, calls, capacity/quarantine, retries and cache hits; successful rows still require all four confidences, support, model/policy identity, input hashes and rationale.

### Eligibility, coverage and fair caps

Acquire the full admitted scope. Label filter-eligible rows in trust order until their compatible quotas are full or the scope is exhausted, within the guarded runtime budgets. Keep source coverage, row eligibility and selection separate. On every production CAT-3 release require the three configured branches current, complete authorized scope receipts, and visible source contribution counts, including zero. A healthy empty branch can be current. Apply the machine gates, conservative dedup and required human resolution before caps; only eligible, supported, review-cleared survivors enter selection. Report uncovered operations, support and class/risk deficits without padding. A contribution is credited once to the survivor's actual origin/branch; alternate origins in the dedup map are provenance, not extra capacity or credit.

For current weighted rows, choose the highest-trust eligible survivors per subrisk after required review. Do not reserve a lower-trust row when stronger sources have filled a subrisk. Expose counts for every source, including zero; absence of a branch contribution does not prevent release. The three mandatory source reservations apply only when reproducing historical unweighted selection.

Fill equal-weight ties deterministically and report actual per-risk and source coverage, deficits and exclusions. Bind the source weight to each selected command in the release manifest. Publication still requires current approval, current rights and verified citations.

### Exact publication authorization

Require a durable authenticated steward attestation for cutover **and every distinct release proposal**. This is separate from actual row decisions. A held or unattested build with completed review reports prepared/waiting, preserves the completion and proposed output, and does not report a failed or published release. The operator hold is an independent veto, stored outside the versioned bundle. Clearing it cannot mint an attestation or a completion; audits record the authenticated actors and transitions.

Add a read-only preparation operation (not a second release asset) producing one canonical proposal manifest and immutable candidate output preview. Bind its digest to partition, registered spec hash and code/policy/selection revisions; current branch terminal and capture-lock digests; current attempts digest and selected row provenance, snippet/capture digests and rights receipts; authoritative review snapshot, batch, decision digest and exact completion token/generation (including policy completion for an empty queue); and ordered survivor IDs with effective labels, output schema, canonical table and CSV hashes. Bind the reconciled coverage report and sampled row IDs to that same digest. The authorized steward attests to the proposal digest after checking at least ten stratified proposed inclusions per branch (all if fewer), including each new origin, inspection and state-changing semantics where present, and automatic and human-reviewed routes where present. Record absent strata, not synthetic decisions. Check source context, flags, class, severity, citation and terms; a material mismatch requires correction and resampling. Store attestation identity, timestamp and revocation state in the existing per-dataset review store. Idempotent continuation of the exact same authorized output can reuse its attestation; any changed binding needs a new one.

The existing `release_admission.write_review_output` boundary is authoritative. Under the per-dataset publication/registry serialization, `publication_authorization` and `review_snapshots` resolve current inputs, reauthorize completion and hold state, recompute effective rows, reservation/fair selection and output bytes using the same pure logic as preview, and require exact attestation match. Serialize authoritative updates of source/evidence bindings and review generation with this check, so a concurrent update either comes first and invalidates the proposal or comes after and marks the committed result stale. On every publication reconcile candidate/filter/outcome/dedup/eligibility/review/cap counts, verify source coverage and reservations, schema/caps and approved rows, require every selected citation resolvable and currently authorized, and reject prohibited examples and unresolved `needs_review`. Verify the exact table/export digests, stage immutable files, and make only the transactionally recorded authorized reference current; failed writes may leave unreferenced objects, never a current release. Apply the same read/current authorization at early return, cached/idempotent result and downstream current lookup; historical inspection stays available.

Verify the CLI, native asset and review continuation share this boundary; include empty-queue policy completion while held, review completion while held, hold clearance without attestation, cached return with a revoked attestation, and concurrent changes to a binding after steward sign-off. No path can substitute a different valid review or export. Rehearse rollback with publication fenced and no restored stale completion.

## Live migration and rollback runbook

These steps are for implementation and deployment after independent rereview and human diagram approval. This design work does not launch runs or inspect credentials.

1. **Baseline and backups.** Run `make remote-up` before Dagster work to reach the shared `codebench` Compose service through localhost `3041`. The recipe uses `--no-recreate`; it verifies availability and does not deploy new code. Read the live `cloud_infrastructure_commands_grounded_v1` registry snapshot, not just the template; record the spec hash, dataset/Dagster homes and partition, artifact backend, currently authorized release/export hash (or absence), current review batch/state, live revision and image/config identity. Verify that build, webserver and daemon use the same homes, durable Postgres namespace and model capacity state. Take and verify recoverable registry, Dagster storage, review DB, object/table storage and release-export backups. Record all locations and timestamps in the private ledger, including immutable historical captures, config and ETL bytes needed for a rebuild.
2. **Deploy compatible code first.** Keep the prepared-source graph semantics and keys usable under the new code. Stage the versioned code/image and UI assets in the existing remote Compose directory using its actual source mount or image configuration; record the previous and new deployment inputs and confirm the running code location reports the candidate revision. If definitions are not hot loaded, agree the shared service reload window and refresh only code-bearing services with their existing volumes and configs; leave `review-db` and persistent volumes in place. Do not bring up a second stack or stop the shared one. Verify webserver/daemon health, the current partition and historical Data/Review/CSV reads before activating the declared-source graph.
3. **Prove reversible rehearsal.** In isolated fixture QA, materialize the prepared-source graph then the declared-source graph in the same test partition; test catalog and capture negatives, full gates and a prepared-manifest rollback build. Carry stable candidate IDs and provenance forward only with verified current source/ETL bindings. Leave legacy semantic manifests, historical assets/config mappings and their materializations immutable and readable. Do not import their texts, passage links or legacy label caches into the declared-source graph; do not seed a new local store or enqueue lookups from the legacy corpus. Measure grounding coverage from actual labeling attempts and failures. Rollback restores compatible historical configuration and graph behavior without promoting any old output to current automatically.
4. **Hold publication and register in place.** Drain in-flight builds/releases for the target partition. Implement a durable per-dataset operator hold, exposed in the CLI or registry control surface and checked transactionally in final publication authorization for CLI, sensors and manual/UI requests. Keep this hold outside the versioned spec so clearing it does not regenerate the review snapshot. It permits collection, labels and review preparation. Persist and audit the hold before registration. Use `dataset_cli validate` then `register` for the reviewed source-declared spec on the existing home, retaining live storage, review settings and batch configuration. Registry registration changes current authorization; the previous release remains available as history, not a substitute for current output. Do not run `build --config` as a shortcut.
5. **Collect, label, review and attest.** Use the preparation-only selection and inspect source rights, coverage and capture locks before allowing inference. When source and capacity gates pass, run `dataset_cli build --dataset cloud_infrastructure_commands_grounded_v1 --home <discovered live home>` with the exact registered spec. Reviewers explicitly complete a resolved nonempty queue; empty queues complete by policy without human decisions. While held, prepare the exact proposal, sample the selected rows and record the authenticated attestation. Only then clear the hold and use the existing release route/continuation. A changed binding leaves the release waiting for a new attestation, even if the hold is clear. Record health, batch/cache telemetry, queue and decision counts, source/operation coverage, proposal/attestation, release asset digest and export checksum. Verify unchanged planning and read-only inspection.
6. **Abort or roll back.** Keep or reinstate the hold if rights, content, currentness, integrity, model capacity, QA or representativeness fails. Stop new launches for that partition, retain all histories, and record failed run and exact diagnostic refs. For runtime incompatibility restore the previous *compatible* image/config after reverting the active spec to the prepared-source graph with a supported registry restore operation that writes an audit event, verifies the expected current revision and invalidates review/release under the same registry serialization. Do not edit the pointer by hand. Retain build history, captures and decisions; do not restore a stale review token, overwrite live Postgres or promote a stale CSV. If the old image lacks the release hold, keep publication entry points fenced during image rollback or restore with the prepared-manifest-compatible new image first. Re-plan the prepared-source graph against archived input pins via current gates; reuse compatible records and decisions, and require a new explicit completion if the restored partition’s queue is nonempty. Validate the resulting snapshot before releasing again. Restore backups only for proven storage damage, after checking for intervening writes; audit the resulting live partition and leave the stack healthy.

The cutover receipt must identify the active code/spec revisions, source capture locks, attempts/evidence receipts and their digests, authenticated reviewer transitions without secret material, branch and finalization run IDs, current publication identity, before/after counts and rollback evidence. Keep it outside Git. Independent delta review checks removal of local RAG without weakening provenance, guard and publication controls; the human owner must approve the revised diagram before implementation.
