# How commands become release rows

**Collection and filtering.** The dataset branch extracts examples from pinned corpora. The documentation branch captures material within a pinned scope to extract candidate commands. Both check origin and usage rights. The Keenable branch extracts examples from returned search snippets, records their provenance and makes no claims about origin rights. At the merge, records keep their branch identities, so the same source identifier in two branches cannot conflate their evidence. The filter examines shell structure and command positions to select candidates for labeling; a match alone does not establish risk.

**Restarting repository capture.** A completed file is the checkpoint: the worker stores its verified bytes by Git blob ID on the dataset volume. If capture stops, rerun the stage on the same volume. It verifies and reuses completed files, downloads unfinished files from the beginning, and retains the failed attempt’s evidence. A checksum without the bytes is not a completed file. A corrupt checkpoint fails verification; a partial collection is never published as a complete table. There is no separate download database to restore.

Capture workers reuse HTTP connections. A pinned GET gets at most four attempts for transient network failures, interrupted transfers, or HTTP 408, 429, 500, 502, 503 and 504. Delays grow exponentially with jitter, with a ten-second maximum wait between attempts. Certificate failures, redirects and integrity mismatches are not reasons to retry. If attempts are exhausted, the stage fails rather than silently dropping the file.

**Resuming Bashguard rule capture.** Use `rules-capture --category <category> --resume-run <uuid>` to resume one failed capture job on the same Dagster instance and private storage. The named run must have a successful in-run settings materialization matching the current registration and a readable final failed attempt. Recovery keeps finished batches and their evidence intact, carries forward accepted rules, and requires an actual finish decision for unfinished batches. The prior evidence remains private and unchanged; the new run writes its own evidence. Omitting `--resume-run` starts a fresh capture.

**Scoring historical actions.** The test split can contain the historical action `modify`. Keep those rows in the denominator with their original labels. A native rule match on such a row is a wrong exact match, even if its category, risk and severity agree; no match is an abstention. `modify` is not an authorable action or a fixture prediction.

**Labeling.** Within each source-trust tier, each candidate gets its own ReAct conversation. `row_concurrency` bounds active conversations (default 8, range 1–64). Each grounding iteration lets the model request multiple `query` or `page_fetch` actions through Keenable MCP and returns all observations before the next model invocation. At most five retrievals run concurrently across rows. Search and fetch share a 10 calls/sec budget per configured organization; keys from the same organization share that budget and its rate-limit cooldown. Bounded retries happen inside the provider, not as additional model turns. Provider incidents are retained separately from the evidence offered to the model. Neither concurrency nor rate is a per-row call budget. The stage has no documentation-capture input. Only fetched pages from configured trusted origins, not collected snippets or example documentation, can support a label.

`maximum_grounding_turns` limits complete model/action/observation iterations (default 5). Mixed finalize and retrieval responses run retrievals and ignore finalize. Malformed nonterminal responses consume an iteration, even if no tool runs. A valid standalone finalize can finish a row early; an unfinished row gets one separate finalize-only invocation after the limit. Zero skips directly to that invocation. Transcripts record `grounding_iterations` and `tool_wave_sizes`, including zero-action rounds. The `started_monotonic_ns` and `finished_monotonic_ns` intervals measure peak active rows within one process. Neither overlapping row intervals nor multi-action requests prove concurrent provider calls.

`risk_candidates` records command-pattern hints, not the allowed answers. An otherwise eligible collected command can have no hints. The model can select any risk defined in the active category. If fetched documentation establishes that none fits, the model returns `reject` with `risk_id: other`. That outcome is an auditable judgment, not a new publishable family. Ambiguous membership calls for review; missing documentation remains an evidence failure. Neither case establishes `other`.

The host validates every row's identity, taxonomy, candidate-assigned evidence, exact quotes and cited URLs. Transcripts, provider receipts and fetched evidence are retained. Only completed successful row conversations are resumable within a matching failed-step retry lineage; changed inputs or a fresh materialization start a new pass. The scheduler credits distinct eligible all-high labels to their resolved family, up to 250 each. A full hinted family does not justify deferral while another family is open; `other` earns no credit.

**Deduplication and eligibility.** Only supported annotations reach deduplication. It collapses proven exact equivalents while retaining links to the original evidence. Different operands, quoting, context or conflicting labels can change the meaning; similarity alone never authorizes a merge. Category eligibility then removes rejected, out-of-category and low category-confidence rows before human review.

**Review and release.** An eligible row can bypass human review only when its label requires no resolution and all four judgments (category, risk, severity and class) have high confidence. Uncertainty or a label requiring resolution goes to a durable review queue. PostgreSQL holds the queue and decisions while reviewers work; no compute worker waits for a person. Decisions can be reused when the original values under review match. Permission to release is separate: it belongs to the current snapshot. An empty queue can complete automatically; a nonempty queue needs terminal decisions and explicit completion. Both paths produce the same release, applying coverage caps after eligibility and approval and reporting shortfalls without padding.
